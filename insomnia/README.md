# Agent API Insomnia collection

Import [agent-api.insomnia.json](agent-api.insomnia.json) using **Import → File** in Insomnia. The file uses the supported Insomnia JSON v4 import format and includes 22 requests. No real credentials are included.

## Setup

1. Configure the root `.env` as described in the project README, including provider credentials, a valid workflow encryption key, and distinct customer/support demo tokens. Preserve an existing workflow key when reusing encrypted workflow data.
2. Start the local services with `docker compose up -d db redis mailpit`, then run `pnpm dev`.
3. In the imported collection's environment, replace `customer_token` with the value of `DEMO_CUSTOMER_TOKEN`. Adjust `agent_url` and `business_url` if your ports differ. Do not put AWS credentials or the workflow key into Insomnia; they stay on the server.
4. Set Insomnia's **Preferences → General → Request / Response → Request timeout (ms)** to `180000` for model streaming. Use development or test mode: demo authentication is disabled in production.

The collection calls the Agent API directly on port 3001, without the frontend's `/agent-api` proxy prefix. The Business API on port 3000 must also be running for customer authentication and tool operations.

## Conversation walkthrough

1. Run **Health and identity** requests to check both applications and your customer token.
2. Run **Conversations → Create conversation**. Its response script saves the returned `conversation_id` automatically and resets retry state.
3. Run **Chat → Send new message**. Edit `message_text` in the environment to ask a different question. The pre-request script generates a fresh UUID and safely encodes the JSON body each time you send.
4. Run **Chat → Follow-up using stored history**. Only the new user text and request ID are sent; the backend supplies history.
5. Run **Conversations → Load history / recover after disconnect** to inspect saved messages, tool results, ordered turns, approval states, and `active`.
6. Once the turn completes, run **Chat → Replay last message**. It reuses the exact ID and text and expects JSON with `replayed: true`, without another model execution. The following conflict request reuses that ID with different text and expects 409.

Message responses are SSE using the AI SDK UI protocol, ending with `data: [DONE]`. You can inspect the raw HTTP response or change the message request to an Event Stream request in Insomnia. After-response scripts check completion and generation error events. If you cancel or time out a stream, repeat the history request until `active` is false. Server execution continues independently of delivery.

Each new-message request stores its ID and text as `last_request_id` and `last_message_text`. Use the explicit replay request for retries: pressing Send on a new-message request creates a new turn. HTTP errors should be checked before replaying; the backend returns 409 while a conversation turn is active.

## Address approval

Run these requests deliberately, rather than executing the entire collection as a batch. Live chat and proposal requests incur model-provider usage. **APPROVE AND APPLY changes the order's delivery address.**

1. Run **Address approval → Request address proposal**. By default, it proposes a change for seeded order `ord_125`, whose status must still allow address changes. You may edit `proposal_text` in the environment.
2. Run **Load history and capture pending proposal**. Its script selects the latest server-stored pending, unexpired proposal and saves `confirmation_id`. Proposals expire after five minutes.
3. Run **APPROVE AND APPLY stored address change** only when you intend to apply that proposal. It sends only `requestId`; order and address come from server storage. The request ID is generated once per confirmation and retained for retries.
4. Load history again to inspect the result. You can duplicate the read-only order request and change `ord_123` to `ord_125` to inspect the updated order directly.

Loading history clears `confirmation_id` when there is no pending, unexpired proposal. The unknown-conversation rejection request checks a nonexistent UUID; it does not simulate another authenticated customer, because the demo authentication configuration exposes only one customer identity.

## Validation requests

The final folder contains expected failures for client-managed history, tool results, malformed request/conversation IDs, text exceeding 4,000 characters, bodies exceeding 100 KiB, invalid authentication, and unknown conversations. Each has a response status assertion. Some request bodies are generated by pre-request scripts, so their visible placeholder JSON is replaced before sending.

The collection does not automatically send subsequent requests or approve changes. It saves returned IDs locally in your selected Insomnia environment. Avoid exporting or committing that environment after adding real tokens.
